# Eureka 源码级面试题集

## 文档说明

基于本仓库源码分析（文档 01-11）整理的面试题集。每题给出**普通答案**（背诵级）和**源码级答案**（区分度所在），并标注代码出处。

---

## 一、基础架构类

### Q1：Eureka 为什么是 AP 而不是 CP？具体体现在哪些设计上？

**普通答案**：Eureka 优先保证可用性，容忍数据不一致。

**源码级答案**：AP 体现在五个具体设计上——
1. **注册不需要多数派确认**：写入本节点内存（双层 ConcurrentHashMap）后立即返回 204，复制是异步的（`PeerAwareInstanceRegistryImpl.register()` 先 `super.register()` 再 `replicateToPeers()`）
2. **复制失败不影响本地结果**：`replicateInstanceActionsToPeers()` 中 catch Throwable 只记日志
3. **自我保护**：网络分区时停止剔除（`isLeaseExpirationEnabled()`），宁可保留可能已死的实例
4. **启动保护期**：节点同步不到数据时拒绝查询（403）而不是返回空——宁可不可用也不给错误数据扩散机会
5. **客户端本地缓存**：注册中心全挂，消费方仍能用缓存调用
> 出处：文档 01/04/05；AbstractInstanceRegistry.java:198、PeerAwareInstanceRegistryImpl.java:507

### Q2：Eureka Server 集群之间是怎么同步数据的？

**普通答案**：节点之间互相复制。

**源码级答案**：三个机制配合——
1. **运行时异步批量复制**：每个写操作（注册/续约/下线）通过批处理框架（500ms 窗口攒批 250 个、taskId 去重）异步发给所有 peer，且只复制一跳（isReplication 标志防止无限转发）
2. **心跳对账修复**：复制心跳时 peer 返回 404 → 把实例推过去；409 → 拉 peer 数据回来覆盖本地。任何复制丢失靠这个机制在分钟级修复
3. **启动全量同步**：新节点启动时 syncUp() 从 peer 拉全量注册表（复用内嵌 EurekaClient 的拉取能力）
> 出处：文档 02/05/09；PeerEurekaNode.java:207（heartbeat 的 handleFailure）

## 二、注册与发现类

### Q3：服务注册的完整流程？注册表用什么数据结构存储？

**源码级答案**：
- 客户端：`InstanceInfoReplicator`（40s 首次延迟）检查脏标记 → `DiscoveryClient.register()` → POST /v2/apps/{appName}
- 服务端：`ApplicationResource.addInstance()` 7 项校验 → `PeerAwareInstanceRegistryImpl.register()` 确定租约时长(默认90s) → `AbstractInstanceRegistry.register()` 写入 → 异步复制
- 数据结构：`ConcurrentHashMap<应用名, Map<实例ID, Lease<InstanceInfo>>>` 双层 Map，外层应用、内层实例，实例被包装成"租约"
- 注册时加的是**读锁**（不是写锁！），允许并发注册；写锁留给增量快照生成
> 出处：文档 01；AbstractInstanceRegistry.java:198

### Q4：为什么注册用读锁、获取增量用写锁？（高区分度）

**源码级答案**：这里的读写锁不是字面的"读/写"语义，而是"互斥组"语义：
- 注册/下线之间**可以并发**（它们只操作内层 ConcurrentHashMap 的不同 key，天然线程安全）→ 共享"读锁"
- 生成增量数据（getApplicationDeltas）需要遍历 recentlyChangedQueue 并计算全量 hashcode，期间**不允许任何注册/下线发生**（否则增量与 hashcode 不一致）→ 独占"写锁"
- 即：N 个注册可并发，但注册与增量快照互斥。这是用锁语义的反转换取注册吞吐
> 出处：文档 01/03；AbstractInstanceRegistry.java:204（read.lock）、:925（write.lock）

### Q5：服务发现（拉取注册表）为什么这么慢？新实例注册后多久能被调用到？

**源码级答案**：最坏约 90 秒，由四级延迟叠加：
1. 服务端 readWriteCacheMap：注册时立即失效（0s）
2. 服务端 readOnlyCacheMap：每 30s 才从 readWrite 同步一次
3. 消费方客户端：每 30s 拉取一次增量
4. Ribbon（如果用）：自己又有 30s 的 ServerList 缓存
优化手段：关闭只读缓存（shouldUseReadOnlyResponseCache=false）、调短各间隔。
> 出处：文档 03/11；ResponseCacheImpl.java:181（同步任务）

## 三、心跳与续约类

### Q6：心跳除了"保活"还有什么作用？（高区分度）

**源码级答案**：心跳是 Eureka 集群数据一致性的"对账巡检"：
- 客户端心跳带 `lastDirtyTimestamp`，服务端 `validateDirtyTimestamp()` 比对版本：客户端新 → 404 让客户端重新注册推新数据；服务端新 → 复制场景返回 409+服务端数据让对方修复
- 节点间复制心跳同理：peer 缺数据（404）→ 推注册过去；peer 数据更新（409）→ 拉回来覆盖本地
- 所以任何历史的复制丢失/数据漂移，都会在下一次心跳（30s 内）被发现并自动修复
> 出处：文档 02；InstanceResource.java:314（validateDirtyTimestamp）、PeerEurekaNode.java:207

### Q7：著名的 Lease.renew() bug 是什么？

**源码级答案**：
```java
public void renew() {
    lastUpdateTimestamp = System.currentTimeMillis() + duration;   // 多加了一个duration!
}
public boolean isExpired(long additionalLeaseMs) {
    return (... currentTimeMillis() > (lastUpdateTimestamp + duration + additionalLeaseMs));  // 又加了一次
}
```
续约时间戳被多加了一个 duration（90s），过期判断时又加一次 duration——实际过期时间是配置的 **2 倍**（180s 而非 90s）。Netflix 在 javadoc 里明确说不修复（影响面太大）。
> 出处：文档 02；Lease.java:77（已加中文注释标注此 bug）

## 四、自我保护与剔除类

### Q8：自我保护机制的触发条件？阈值怎么算？

**源码级答案**：
- 触发条件：最近一分钟全局续约数 ≤ 阈值（numberOfRenewsPerMinThreshold）
- 阈值 = 期望客户端数 × (60/30) × 0.85，即每个客户端每分钟预期 2 次心跳的 85%
- 例：100 个实例 → 阈值 = 100 × 2 × 0.85 = 170 次/分钟，实际续约低于 170 → 自我保护触发 → EvictionTask 直接 return 不剔除任何实例
- 期望客户端数的维护：注册+1、主动下线-1、剔除不变（！）、每 15 分钟用实际值校准（且只升不降）
> 出处：文档 04；AbstractInstanceRegistry.java:1276（updateRenewsPerMinThreshold）、PeerAwareInstanceRegistryImpl.java:507

### Q9：为什么"剔除"不复制给其他节点，而"主动下线"要复制？（高区分度）

**源码级答案**：这是 evict() 调用 `internalCancel()` 而不是 `cancel()` 的原因——
- 如果剔除被复制，peer 节点会把它当作"主动下线"处理，导致 peer 的 expectedNumberOfClientsSendingRenews 减 1 → 自我保护阈值跟着下降 → **该触发自我保护时不触发**（阈值随着剔除不断自我放松）
- 正确语义：剔除是每个节点根据自己收到的心跳独立判断的（你没收到心跳不代表我没收到——网络分区场景下这是保命的设计）
> 出处：文档 04；AbstractInstanceRegistry.java:330 注释、:650（evict 调 internalCancel(appName,id,false)）

### Q10：单次剔除任务最多剔除多少实例？为什么要随机剔除？

**源码级答案**：
- 上限 = 注册表大小 × (1 - 0.85) = 15%。即使有 100 个过期实例，单轮也只剔除 15 个，分多轮渐进——每轮之间自我保护有机会重新触发（刹车机制）
- 随机（Knuth 洗牌）：如果按遍历顺序剔除，同一应用的实例是相邻的，可能一轮就把某个应用的实例全剔光；随机化把影响均匀分散到所有应用
> 出处：文档 04；AbstractInstanceRegistry.java:650（evict 中文注释详细标注三层保护）

## 五、缓存与性能类

### Q11：Eureka Server 的三级缓存结构？为什么要这么设计？

**源码级答案**：
- 真实数据：registry（双层 Map）→ 二级：readWriteCacheMap（Guava，180s 过期，写时主动失效）→ 一级：readOnlyCacheMap（普通 Map，30s 定时同步，请求默认读这里）
- 缓存的不是对象，是**序列化+压缩后的字节**——成千上万客户端拉同一份注册表，序列化只做一次（缓存 Key 含格式维度：JSON/XML × full/compact × gzip）
- 为什么两级：readWrite 保证"最终会更新"（失效+过期兜底），readOnly 保证"读取零竞争"（无锁无回源）。代价是 30s 延迟
> 出处：文档 03；ResponseCacheImpl.java:120/125（已加中文注释）

### Q12：增量拉取怎么保证不丢数据？

**源码级答案**：hashcode 校验 + 全量兜底：
- 服务端增量响应附带"全量 hashcode"（格式 `UP_10_DOWN_2_`，按状态统计实例数）
- 客户端合并增量后计算本地 hashcode，不一致（说明丢过增量/乱序）→ 立即触发全量拉取覆盖
- 增量数据本身来自 recentlyChangedQueue（保留 3 分钟），客户端 30s 拉一次，留了 6 倍安全余量
> 出处：文档 03；DiscoveryClient.java:1191（getAndUpdateDelta，已加中文注释）、Applications.java:319

## 六、工程设计类

### Q13：Eureka 客户端的定时任务为什么不用 scheduleAtFixedRate？

**源码级答案**：用的是"自调度"模式（TimedSupervisorTask）：每次执行完再调度下一次。
- fixedRate 的问题：任务超时（网络故障时心跳必然超时）会导致任务在队列中堆积，恢复后集中爆发
- TimedSupervisorTask 的设计：子任务提交线程池限时等待（30s），超时则下次调度间隔翻倍（指数退避，上限 10 倍即 300s），成功后恢复正常间隔
- 隐患：退避上限 300s 超过了租约过期时间 180s——长时间网络故障恢复前实例可能已被剔除
> 出处：文档 02；TimedSupervisorTask.java:70（已加中文注释）

### Q14：批处理复制框架的去重机制？什么情况下复制会丢？

**源码级答案**：
- 去重：任务以 taskId（"register#应用名/实例ID"）为 key 存入 pendingTasks Map，相同 key 的新任务直接覆盖旧任务（overriddenTasks 计数）——同一实例 500ms 内心跳两次只复制最后一次
- 会丢的三种情况：①任务过期（积压超过 expiryTime，expiredTasks 计数）②队列溢出（>10000，queueOverflows 计数）③PermanentError（4xx 响应）
- 丢了不要紧：下一次心跳复制的 404/409 对账机制会把数据补齐——这是"复制尽力而为+心跳兜底"的整体设计
> 出处：文档 09；AcceptorExecutor.java:277（appendTaskHolder）

### Q15：运维把实例设为 OUT_OF_SERVICE 后，实例的心跳会把状态改回 UP 吗？

**源码级答案**：不会。状态由规则链裁决（FirstMatchWinsCompositeRule）：
- 实例心跳自报 UP → 规则① DownOrStartingRule 不匹配（只信"自报坏"）→ 规则② OverrideExistsRule 发现覆盖状态存在 → 用 OUT_OF_SERVICE 压制
- 直到运维 DELETE /status 删除覆盖状态才恢复
- 注意坑：覆盖状态 1 小时无访问会自动过期（Guava expireAfterAccess），但租约里的状态还是 OUT_OF_SERVICE，会被规则③ LeaseExistsRule 继续维持——所以正确的恢复操作必须走 DELETE 接口
> 出处：文档 07；OverrideExistsRule.java（已加中文注释）

## 七、对比与选型类

### Q16：Eureka 和 Nacos/Consul 怎么选？

**源码级答案**：见文档 10 的完整对比表。核心论点：
- Eureka 故障检测慢（~5分钟，源码层面是 30s 心跳+180s 过期+60s 剔除+90s 缓存的叠加），Nacos 临时实例 ~30s
- Eureka 只有拉模式（30s 周期），Nacos/Consul 有推送
- Eureka 1.x 已停止新特性开发
- 但 Eureka 的 AP 设计思想（自我保护/对账修复/多级缓存）被 Nacos AP 模式大量借鉴，学习价值不减
