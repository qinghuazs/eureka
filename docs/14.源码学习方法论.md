# 源码学习方法论：五阶段闭环

> 本方法论从本仓库的 Eureka 源码学习实践中提炼（2026-06，dongmian 分支全部产出即其产物），
> 可直接套用于任何中大型开源项目（Nacos / Sentinel / RocketMQ / Kafka...）。
> 每个阶段都标注了"Eureka 实例"——方法论中的每句话都有对应的真实产出佐证。

---

## 总览

```
┌──────────────────────────────────────────────────────────────────┐
│  ① 建图 → ② 按流程深挖 → ③ 横向补全 → ④ 真实验证 → ⑤ 输出内化      │
│   半天      每条1~2天        2~3天        1~2天        2~3天        │
│      ↑                                                  │          │
│      └───────────────── 下一个项目复用 ←─────────────────┘          │
└──────────────────────────────────────────────────────────────────┘

一个 2 万行核心代码的项目，完整走完五阶段约需 2~3 周（每天 2~4 小时）。
```

核心思想一句话：**用"写"对抗遗忘，用"跑"对抗错觉，用"教"检验理解。**

---

## 阶段①：建图 —— 先有地图，再走路

**目标**：把"几十万行代码"压缩成"几条主线"，确定读什么、不读什么。

| 步骤 | 操作 | 产出 |
|------|------|------|
| 1.1 摸模块 | 看构建文件（settings.gradle / pom.xml），给每个模块标注 必读★ / 了解 / 跳过 | 模块职责表 |
| 1.2 识流程 | 自问"这个系统的本质是什么"，列出 3~6 条生命周期级核心流程 | 流程清单 |
| 1.3 定入口 | grep 关键词定位每条流程的入口类与方法，记录 文件:行号 | 流程→入口映射表 |
| 1.4 写指南 | 把以上三者整合成第一份文档 | `docs/源码阅读指南.md` |

**Eureka 实例**：10 个 Gradle 模块 → 只有 client / core / server 必读；
本质是"服务注册与发现" → 5 条流程（注册/续约/拉取/下线/启动）；
产出 `源码阅读指南.md`（含速查表）。

**判断标准**：建图完成的标志是——你能在 30 秒内回答"X 功能的代码大概在哪个模块的哪个类"。

**反模式**：
- ❌ 从 main 函数 / 第一个包开始顺序读
- ❌ 直接扎进最复杂的类（如一上来就读 ResponseCacheImpl）
- ❌ 跳过建图直接深挖（没有地图的深挖 = 迷路）

## 阶段②：按流程深挖 —— 核心引擎

**目标**：每条流程做到"从入口到落库每一行都明白为什么"。

每条流程跑一个固定的**四步小闭环**：

### a. 追链路

grep 定位这条流程从触发到结束经过的所有方法（通常跨客户端/服务端/存储层）。
画出调用链草稿：`入口REST → 业务层 → 存储层 → 副作用(缓存/队列/复制)`。

### b. 写注释（理解的"写入"）

给链路上每个核心方法加母语注释。纪律：

- **只加注释，零代码变更**——用 `git diff` 验证每一行新增都以注释符号开头
- **写"为什么"不写"是什么"**——`i++ // i加1` 是垃圾；`// 期望续约客户端数+1,用于自我保护阈值计算` 才有价值
- **标注三件事**：调用来源（谁会调这个方法）、设计意图（为什么这么写）、已知坑（如 Lease 的 2倍duration bug）

### c. 写文档（固定模板）

```
零、TL;DR           一句话摘要 + 复杂度域 + 关键风险点
一、业务上下文       术语表 / 业务不变量 / 触发方式
二、系统协作         C4 上下文图
三、ADR 设计决策表   为什么这么设计 / 备选方案 / 代价   ★ 灵魂章节
四、核心流程         时序图(autonumber) + 流程图 + 状态机
五~八、校验/外部交互/NFR/错误码表/FMEA失败模式
九~十一、影响半径 / 测试与可观测性 / 代码位置索引(含行号)
十二~十四、技术债 / 排查FAQ(决策图) / 元信息
```

ADR 表是灵魂：每个非平凡设计都要回答"为什么不用更简单的方案"。
能写出 ADR = 真正理解了；只能复述代码 = 还没理解。

### d. 提交

一条流程 = 一个 commit。消息格式：`docs: XX流程深入分析(中文注释+流程文档)` + 要点列表。

**Eureka 实例**：5 条流程 = 5 个 commit（f52ab262 ~ cf4c287b），
每个含 ~100 行注释 + ~600 行文档。

**时间分配参考**：追链路 20% / 写注释 30% / 写文档 40% / 提交整理 10%。

---

## 阶段③：横向补全 —— 填掉"提到但没展开"的洞

**目标**：把深挖时记下的支线清单消化掉。

深挖时会不断遇到"这里先不展开"的部分。处理规则：

1. 遇到就记入清单（不要当场展开，会打断主线）
2. 所有流程做完后统一回收
3. **筛选标准：被 ≥2 条流程引用的支线才值得补**，只出现一次的跳过

**Eureka 实例**：传输层（被注册/续约/拉取都引用）→ 文档06；
状态规则链（被注册/续约引用）→ 文档07；
数据模型+序列化+批处理（被所有流程引用）→ 文档09。
而 AWS 专属代码（只被启动流程提到一次）→ 跳过。

## 阶段④：真实验证 —— 不跑通不算懂

**目标**：让每个文档结论都有运行证据。这是最容易被省略、也最不能省的阶段。

三层验证，层层递进：

### 第一层：环境层（让它跑起来）

老项目在新环境编译运行必然遇到坑（工具链版本/网络/平台差异）。
**把每个坑和解法记成文档**——这份文档对后来者的价值往往超过源码分析本身。

Eureka 实例：JDK21 编译 target 1.8、阿里云镜像 init 脚本、测试端口冲突 → 文档08。

### 第二层：官方测试层（确认行为与文档一致）

跑项目自带的单元测试和集成测试。重点找"集成测试"——它们往往会启动真实服务，
是验证全链路理解的捷径。

Eureka 实例：EurekaClientServerRestIntegrationTest 启动真实 Jetty + war，
7 个端到端测试覆盖了文档 01/02/04/05 的全部结论。

### 第三层：自建验证层（把论断变成断言）★ 精髓

为文档中的每个关键论断写一个 JUnit 测试：

```
文档说"Lease 有 2倍duration 的 bug"
  → 测试: 1.5倍时间断言未过期 + 2.5倍时间断言已过期
文档说"运维覆盖状态会压制实例自报的UP"
  → 测试: 构造规则链,断言最终状态为 OUT_OF_SERVICE
```

**测试通过 = 理解正确；测试本身又成了可执行的文档。**
这些测试放在源码树的独立包里（如 `com.netflix.eureka.learning`），与项目一起编译运行。

Eureka 实例：LearningVerificationTest，11 个测试钉住 11 个论断，全部通过。

## 阶段⑤：输出内化 —— 费曼检验

**目标**：讲不出来就是没学会。按"压缩比"递增做三种输出：

| 输出物 | 压缩方式 | 检验什么 | Eureka 实例 |
|--------|---------|---------|------------|
| **全景大图** | 把所有文档压成几张图 + 时间链 | 能否一张图讲清全系统 | 文档11 |
| **面试题集** | 每题"普通答案 vs 源码级答案"对照 | 能否区分背诵和理解 | 文档12（16题） |
| **博客系列** | 每篇从问题/事故切入重新叙事 | 能否教会完全不懂的人 | blog/01-10 |

**博客的固定骨架**（亲测有效）：

```
问题开头（面试题/生产事故/反直觉现象,绝不用定义开头）
→ 源码解析（每篇只留1-2个核心代码片段,每段≤15行）
→ 设计模式提炼（这个设计能迁移到什么地方）
→ 面试官视角（普通回答 vs 加分回答）
→ 一句话总结 + 下篇预告（连载钩子）
```

## 贯穿全程的 5 条纪律

| # | 纪律 | 一句话解释 |
|---|------|-----------|
| 1 | **流程驱动，不是文件驱动** | 永远在追"一个请求的旅程"，而不是"把这个类读完" |
| 2 | **写入式学习** | 注释、文档、测试都是"写"。只读不写，三天就忘 |
| 3 | **结论双重锚定** | 每个结论 = 代码出处(文件:行号) + 运行证据(测试/日志)。缺一个就标"推测，待确认" |
| 4 | **小步提交** | 一条流程一个 commit。做废了精确回滚，做好了历史就是学习日志 |
| 5 | **工具链质检** | 图要真渲染(mermaid-cli)、链接要真有效、测试要真运行。"看起来对"≠"验证过对" |

## 与 AI 协作的分工（如果使用 AI 辅助）

本方法论在 AI 辅助下效率可提升 3~5 倍，但分工必须清晰：

| 环节 | AI 做 | 人做 |
|------|-------|------|
| 建图 | 并行探索模块结构、定位入口 | 判断哪些流程是"核心"（需要业务嗅觉） |
| 追链路 | grep/阅读/整理调用链 | 抽查验证关键跳转 |
| 写注释 | 起草注释 | **逐条审阅**——注释里的错误理解会固化 |
| 写文档 | 按模板生成 | 审 ADR 章节（设计权衡最容易写错） |
| 验证 | 搭环境、跑测试、写验证测试 | 看测试断言是否真的对应文档论断 |
| 输出 | 起草博客/面试题 | 用自己的话重讲一遍（内化的最后一步） |

**红线**：AI 生成的任何"论断"，没有代码出处和运行证据的，一律标注"待验证"。
