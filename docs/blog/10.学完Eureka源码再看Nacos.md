# 学完 Eureka 源码再看 Nacos：注册中心的演化与选型

> 本文是《Eureka 源码深度解析》系列第 10 篇（完结篇）。
> 前九篇深扎源码，这一篇抬头看路：Eureka 的设计放在 2026 年还成立吗？

## 注册中心的本质：四个问题

读完 Eureka 源码会发现，所谓注册中心，无非是对四个问题的回答：

1. **怎么知道实例活着？**（健康检测）
2. **数据存在哪、怎么同步？**（一致性模型）
3. **消费方怎么拿到数据？**（发现机制）
4. **网络出问题时怎么办？**（分区容错策略）

Eureka、Nacos、Consul、Zookeeper 的区别，就是四道题答案的排列组合。

## 四道题，四种答案

### 第一题：健康检测

| | 方式 | 检测延迟 |
|--|------|---------|
| **Eureka** | 客户端心跳（30s）+ 租约过期（实际180s）+ 剔除周期（60s） | **约 5 分钟** |
| **Nacos** | 临时实例心跳 5s,15s 标不健康,30s 剔除 | 约 30 秒 |
| **Consul** | Server 主动探测（TCP/HTTP/gRPC,可秒级） | 秒级 |
| **Zookeeper** | TCP 会话 + 临时节点 | 会话超时（秒级） |

Eureka 慢的原因在源码里看得清清楚楚（系列第 2、4 篇）：30s 心跳是写死的文化惯例、
租约过期有个 2 倍 bug、剔除还有三层保护。每一层都有理由，叠起来就是 5 分钟。

这是 Eureka 在 2026 年最大的短板。

### 第二题：一致性

| | 模型 | 协议 |
|--|------|------|
| **Eureka** | AP,最终一致 | 无协议:异步复制+心跳对账（系列第1、2、9篇） |
| **Nacos** | AP（临时实例,Distro协议）/ CP（持久实例,Raft）可选 | Distro / Raft |
| **Consul** | CP | Raft |
| **Zookeeper** | CP | ZAB |

有意思的是 Nacos 的 Distro 协议——读它的设计文档会有强烈的既视感：
每个节点负责一部分数据、异步复制给其他节点、定期校验数据一致性并修复……
**这就是 Eureka 模式的协议化重构。** Eureka 用心跳搭便车做对账，
Distro 把对账抽成了独立的定时校验任务。思想同源。

### 第三题：发现机制

| | 方式 | 变更感知延迟 |
|--|------|------------|
| **Eureka** | 客户端定时拉取（30s）+ 多级缓存 | 最坏 90 秒（系列第3篇） |
| **Nacos** | 拉取 + **UDP推送**（1.x）/ gRPC长连接推送（2.x） | 秒级 |
| **Consul** | blocking query（长轮询） | 秒级 |
| **Zookeeper** | Watch 回调 | 秒级 |

Eureka 是四者中唯一没有"推送"能力的。这是架构层面的差距，不是调参能弥补的。

### 第四题：分区容错

| | 行为 |
|--|------|
| **Eureka** | 自我保护:保留数据继续服务,分区愈合后对账（系列第4篇） |
| **Nacos AP** | 类似 Eureka |
| **Consul / ZK** | 少数派分区**完全不可用**（不能读也不能写） |

这道题 Eureka 的答案至今仍是教科书级的——对服务发现这个场景，AP 就是比 CP 合理。
连 Consul 后来都加了 stale read 模式来缓解 CP 的可用性问题。

## 所以，2026 年怎么选？

| 场景 | 选择 | 一句话理由 |
|------|------|----------|
| 国内新项目 | **Nacos** | 注册+配置一体,推送快,文档生态友好,Eureka思想的现代化继承者 |
| 海外/多云/服务网格 | **Consul** | 多DC原生,Connect服务网格 |
| Kubernetes 环境 | **K8s Service** | 平台已内置,别叠床架屋 |
| 存量 Spring Cloud Netflix | 不动 或 平滑迁 Nacos | Eureka 1.x 仍稳定,但没有未来 |
| **学习分布式系统** | **读 Eureka 源码** | 见下文 |

## 为什么学习首选还是 Eureka？

这是写完整个系列后我最想说的：

1. **代码量刚好**：核心逻辑 2 万行左右，一两周能读完。Nacos 30 万行起步，
   第一个源码项目选它会淹死在细节里。

2. **机制完整且自洽**：注册/心跳/缓存/剔除/复制/自愈，麻雀虽小五脏俱全。
   而且每个机制都能用"AP 优先"这一条主线串起来——这种设计一致性本身就是最好的教材。

3. **思想可迁移**：心跳对账（Nacos Distro 的前身）、多级缓存（一切读多写少系统的标配）、
   自我保护（所有故障检测系统都要面对的"误判"问题）、攒批去重（Kafka/日志系统同款）……
   学的是 Eureka，用的地方远不止注册中心。

4. **能跑起来**（系列第 8 篇）：51 个测试在 2026 年的机器上依然全绿。
   一个能验证的系统才是真正属于你的知识。

## 系列后记

十篇文章，从一次注册请求出发，走完了 Eureka 的全部核心链路：

> 注册（1）→ 心跳与对账（2）→ 缓存与发现（3）→ 剔除与自我保护（4）→
> 服务端启动（5）→ 客户端容错（6）→ 状态裁决（7）→ 实践验证（8）→
> 复制框架（9）→ 行业对比（10）

如果说有什么是比具体机制更值得带走的，那就是 Eureka 用整个系统回答的那个问题：

**当你无法同时拥有一致性和可用性时，怎样把"不一致"的代价降到业务可以接受的程度？**

Eureka 的答案：让一切都最终收敛（循环+对账），让一切延迟都有明确上界（30s/90s/5min），
让一切失败都有兜底（重试/隔离/全量修复）。

这个答案，比 Eureka 本身活得更久。
