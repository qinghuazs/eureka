# Eureka Server 启动时都干了什么？聊聊"服务端同时是客户端"的自举设计

> 本文是《Eureka 源码深度解析》系列第 5 篇。前四篇都站在客户端视角，
> 这一篇换位：一个 Eureka Server 从启动到对外服务，中间发生了什么？

## 一个容易被忽略的事实

先抛一个问题：Eureka Server 集群的节点之间，是怎么互相发现的？

Nacos 用 Raft 协议选主，Zookeeper 有 ZAB，Consul 有 Gossip + Raft……
那 Eureka 呢？答案可能让你意外：

**Eureka Server 之间互相发现的方式，就是服务发现本身。**

每个 Eureka Server 内部都嵌着一个 EurekaClient（DiscoveryClient），
这个内嵌客户端做的事和你的微服务一模一样：向其他 Server 注册自己、发心跳、拉注册表。

换句话说：**Eureka Server 是自己的第一个用户。** 这种"用自己实现自己"的设计叫自举（bootstrap）。

## 启动八步曲

Eureka Server 是个 war 包，启动入口是 web.xml 里注册的 ServletContextListener
（EurekaBootStrap）。容器启动时回调它，依次做八件事：

```
① 加载服务端配置（eureka.server.*）
② 创建内嵌 EurekaClient ←—— 关键！它会立刻向 peer 注册自己、拉取注册表
③ 创建注册表（PeerAwareInstanceRegistryImpl）
④ 创建 PeerEurekaNodes（peer 节点管理器,解析 serviceUrl、剔除自己）
⑤ 初始化上下文（启动复制统计、响应缓存、阈值校准任务）
⑥ syncUp() ←—— 从 peer 同步存量注册表
⑦ openForTraffic() ←—— 开放流量,把自己标记为 UP
⑧ 注册监控指标
```

重点看 ⑥ 和 ⑦。

## syncUp：搬运工的智慧

新节点加入集群，怎么获得已有的注册数据？你可能想象需要一个专门的"数据同步协议"。

但 Eureka 的实现简单到令人发指（PeerAwareInstanceRegistryImpl.syncUp）：

```java
for (int i = 0; i < serverConfig.getRegistrySyncRetries() && count == 0; i++) {
    if (i > 0) Thread.sleep(30000);                       // 重试间隔30s
    Applications apps = eurekaClient.getApplications();   // 读内嵌客户端的本地缓存！
    for (Application app : apps.getRegisteredApplications()) {
        for (InstanceInfo instance : app.getInstances()) {
            register(instance, ..., true);                 // 逐条"复制注册"进自己的注册表
        }
    }
}
```

没有同步协议。第②步创建的内嵌客户端早就把 peer 的注册表拉到本地缓存了，
syncUp 只是把这份缓存逐条搬进自己的注册表。**复用客户端的拉取能力，零额外协议。**

重试逻辑也很直白：拿到 0 条数据就重试（最多 5 次，间隔 30 秒）。
什么情况会拿到 0 条？——你是集群启动的第一个节点，根本没有 peer 可以同步。

## openForTraffic 与启动保护期

同步完成后开放流量：

```java
public void openForTraffic(ApplicationInfoManager applicationInfoManager, int count) {
    this.expectedNumberOfClientsSendingRenews = count;    // 用同步到的实例数初始化自我保护基数
    updateRenewsPerMinThreshold();
    ...
    if (count > 0) {
        this.peerInstancesTransferEmptyOnStartup = false;
    }
    applicationInfoManager.setInstanceStatus(InstanceStatus.UP);   // 我准备好了！
    super.postInit();                                              // 启动剔除定时任务
}
```

注意那个 `count > 0` 的判断。如果 syncUp 一条数据都没拿到（count=0），
节点会进入**启动保护期**：接下来 5 分钟内，所有查询请求一律返回 403。

为什么？想象没有这个保护：

1. 节点启动，注册表为空
2. 某个消费方恰好从这个节点拉取注册表 → 拿到空列表
3. 消费方的本地缓存被空列表覆盖 → **它眼中所有服务都消失了**
4. 这个消费方的所有调用全部失败

一个空注册表比一个不可用的注册中心危险得多。
所以 Eureka 选择：**宁可拒绝服务（403，客户端会重试别的节点），也不返回错误数据。**

> 这就是为什么单机部署 Eureka 时，启动后 5 分钟内 Dashboard 一直报错——
> 你是第一个节点，syncUp 必然为空，必然进保护期。
> 测试环境加上 `eureka.waitTimeInMsWhenSyncEmpty=0` 就能跳过。

## 集群复制的发动机：批处理框架

启动完成后，运行期节点之间的数据同步靠复制。第 1 篇提过复制是"攒批+异步"的，
这里看看这台发动机的内部（util/batcher 包）：

```
复制任务 → 接收队列 → [调度线程] → 去重池 → 攒批 → 批量队列 → [工作线程×20] → 一个HTTP请求发给peer
                          ↑                                          |
                          └────── 失败回流（重做队列）←──────────────┘
```

三个机关：

1. **去重**：任务以 "register#应用/实例ID" 为 key 存 Map，相同 key 新覆盖旧。
   同一实例 500ms 内心跳两次？只复制最后一次。
2. **攒批**：满 250 个任务或最老的任务等了 500ms，打包成一个 HTTP 请求。
   万级实例集群的复制请求数因此降低 95% 以上。
3. **过期丢弃**：任务积压超过期限直接扔（反正心跳对账会兜底，见第 2 篇）。

## 面试官视角

**Q：三个 Eureka Server 组成集群，配置文件怎么写？为什么要互相指向？**

加分回答：每个节点的 `eureka.client.serviceUrl.defaultZone` 指向**另外两个**节点。
原理是 Server 内嵌的 EurekaClient 用这个配置去找 peer：向它们注册自己（所以你能在 A 的
控制台看到 B 和 C）、从它们 syncUp 数据、向它们复制写操作。
PeerEurekaNodes 解析这个列表时会自动剔除指向自己的 URL，所以三个节点配置可以完全一样。

## 一句话总结

Eureka Server 的启动哲学是"自举 + 保守"：用自己（内嵌客户端）发现集群、搬运数据；
数据没准备好时宁可拒绝服务也不裸奔。集群运行期的同步则全靠"批处理复制 + 心跳对账"这对组合拳。
