# 运维摘流后实例为什么不会自己恢复？Eureka 状态规则链解析

> 本文是《Eureka 源码深度解析》系列第 7 篇。这篇从一个运维操作切入，
> 讲清楚 Eureka 里"实例状态"到底由谁说了算。

## 一次灰度发布

灰度发布的标准流程：

```bash
# 1. 把旧实例摘流（不杀进程,只是不让流量进来）
curl -X PUT "http://eureka:8761/eureka/apps/MY-APP/instance-1/status?value=OUT_OF_SERVICE"

# 2. 观察新实例运行正常

# 3. 恢复或下线旧实例
```

第 1 步执行后，instance-1 的状态变成了 OUT_OF_SERVICE，消费方不再调用它。

但等等——instance-1 的进程还活着，它的心跳还在每 30 秒发一次，心跳里报告的状态是 UP。
为什么这些心跳没有把状态改回 UP？

更进一步：instance-1 如果重启了，重新注册时报告的状态也是 UP，为什么注册也改不回来？

## 状态的三个声音

一个实例的状态，同时有三方在"发声"：

| 声音 | 内容 | 存在哪 |
|------|------|--------|
| 实例自己 | "我是 UP"（健康检查通过） | 心跳/注册请求里的 status 字段 |
| 运维 | "我把它设为 OUT_OF_SERVICE" | 服务端的 overriddenInstanceStatusMap |
| 服务端历史 | "我记录里它是 OUT_OF_SERVICE" | 注册表中租约里的 InstanceInfo.status |

三方冲突时听谁的？Eureka 用一条**规则链**（责任链模式）来裁决，
每次注册和续约都会执行（FirstMatchWinsCompositeRule）：

```
规则① DownOrStartingRule: 实例自报 DOWN/STARTING？ → 是 → 直接采纳（实例说自己坏,直接信）
        ↓ 否（实例自报UP）
规则② OverrideExistsRule: 运维设置过覆盖状态？ → 是 → 用覆盖状态 ★摘流靠这条压制★
        ↓ 否
规则③ LeaseExistsRule: 服务端已有UP/OUT_OF_SERVICE记录？ → 是 → 沿用记录
        ↓ 否
规则④ 兜底: 采纳实例自报状态
```

## 回答开头的问题

**心跳为什么改不回状态？**

心跳自报 UP → 规则① 不匹配（只信"自报坏"，不信"自报好"）→ 规则② 发现运维的覆盖状态
还在 map 里 → 用 OUT_OF_SERVICE 压制。心跳发一万次也是这个结果。

**这个设计的精髓在规则①的"非对称信任"**：

- 实例说自己**坏**（DOWN/STARTING）→ 无条件相信。它最清楚自己的健康检查结果，谎报"坏"没有动机。
- 实例说自己**好**（UP）→ 必须过堂。因为可能有运维的意志（覆盖状态）需要凌驾于它之上。

一句话：**坏消息直通，好消息过审。**

## 恢复操作的坑

灰度结束想恢复 instance-1，正确操作是：

```bash
curl -X DELETE "http://eureka:8761/eureka/apps/MY-APP/instance-1/status?value=UP"
```

注意必须用 DELETE 接口（它会删除覆盖状态**并**把实例状态显式设回 UP）。

有一个著名的坑：覆盖状态存储用的是 Guava Cache，配置了 **1 小时无访问自动过期**。
你可能会想：那我等 1 小时它自己恢复不就行了？

不行。覆盖状态过期只是规则②不再匹配，但规则③（LeaseExistsRule）会接手——
服务端租约里记录的状态还是 OUT_OF_SERVICE，规则③会继续维持它。

结果就是：**实例卡在 OUT_OF_SERVICE 状态，覆盖状态却已经查不到了**，
排查时一脸懵逼。这是 Eureka 状态管理最容易踩的坑。

> **设计模式提炼**：责任链的每个规则独立可测试、可插拔（AWS 版本就在链中多插了一条
> AsgEnabledRule）。但链式裁决的代价是"状态恢复路径不唯一"——多条规则都可能维持同一个状态，
> 删除其中一个条件不代表状态会变。设计这类系统时，要给每个状态提供一个**明确的、唯一的**
> 恢复操作（Eureka 的答案就是 DELETE /status 接口）。

## 面试官视角

**Q：Eureka 实例的状态有几种？OUT_OF_SERVICE 和 DOWN 有什么区别？**

加分回答：五种——UP / DOWN / STARTING / OUT_OF_SERVICE / UNKNOWN。
DOWN 是实例**自己**报告的（健康检查失败），实例恢复后自己就能报回 UP；
OUT_OF_SERVICE 通常是**运维**通过覆盖状态设置的，实例自己报什么都没用，
必须运维显式删除覆盖才能恢复。一个是"我病了"，一个是"领导让我停职"——
病好了能自己回来上班，停职必须领导批准复职。

## 一句话总结

实例状态由规则链裁决：自报故障 > 运维覆盖 > 服务端记录 > 自报正常。
记住"坏消息直通，好消息过审"，以及恢复必须走 DELETE /status 接口。
