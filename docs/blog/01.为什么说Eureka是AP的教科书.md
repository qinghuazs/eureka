# 为什么说 Eureka 是 AP 的教科书？从一次注册请求说起

> 本文是《Eureka 源码深度解析》系列第 1 篇。代码基于 Netflix Eureka 1.x（master 分支），
> 配套的中文注释版源码和全部分析文档在 GitHub 仓库 dongmian 分支的 docs/ 目录。

## 一个看似简单的问题

面试官："服务往 Eureka 注册的时候，Eureka 集群是怎么保证其他节点也能拿到这个注册信息的？"

候选人 A："节点之间会互相同步。"

候选人 B："注册请求写到一个节点后，这个节点会异步把它复制给其他节点；复制是不保证成功的，
丢了也没关系，因为之后每 30 秒一次的心跳复制会发现数据缺失并自动补齐——所以 Eureka 的
集群一致性是『最终一致』，这是它选择 AP 的直接体现。"

这两个回答的差距，就是这篇文章要填平的。

## 注册请求的完整旅程

### 第一站：客户端，一个被延迟了 40 秒的请求

很多人以为服务一启动就会注册到 Eureka。看代码（DiscoveryClient 初始化定时任务）：

```java
// InstanceInfoReplicator.start()
public void start(int initialDelayMs) {       // initialDelayMs 默认 40 秒！
    if (started.compareAndSet(false, true)) {
        instanceInfo.setIsDirty();            // 关键：先标记"脏"
        Future next = scheduler.schedule(this, initialDelayMs, TimeUnit.SECONDS);
        scheduledPeriodicRef.set(next);
    }
}
```

为什么延迟 40 秒？因为实例的 IP、端口、健康检查状态可能还没就绪。Eureka 宁可晚注册，
也不注册一份不完整的数据然后频繁更新。

注意那个 `setIsDirty()`——Eureka 客户端的注册不是"调用一次注册方法"，而是一个**持续运行的
对账循环**：每 30 秒检查一次"我本地的实例信息和服务端是否一致（脏标记）"，不一致就重新注册。
首次注册只是这个循环的第一次执行。

> **设计模式提炼**：把"一次性动作"建模成"持续收敛的循环"，是分布式系统对抗不确定性的通用手法。
> 注册请求可能失败、网络可能抖动——但只要循环还在，状态终将收敛。

### 第二站：服务端，一把"反着用"的读写锁

请求到达服务端 `AbstractInstanceRegistry.register()`，第一行代码就值得玩味：

```java
public void register(InstanceInfo registrant, int leaseDuration, boolean isReplication) {
    read.lock();    // 注册——一个"写"操作——加的是【读锁】？！
    try {
        ...
        gMap.put(registrant.getId(), lease);    // 写入注册表
```

注册明明是写操作，为什么加读锁？

因为这里的读写锁不是字面的"读/写"语义，而是**互斥分组**：
- 注册、下线之间可以**并发**（它们操作 ConcurrentHashMap 的不同 key，本身线程安全）→ 共享"读锁"
- 生成增量快照（getApplicationDeltas）需要数据冻结的一瞬间 → 独占"写锁"

也就是说：**N 个注册可以同时进行，但注册和"读取增量"互斥**。
锁的命名遵循的是"谁多谁用读锁"的吞吐优化原则，而不是操作的读写性质。

### 第三站：注册表，一个"租约"的诞生

实例信息不是直接存进 Map 的，而是被包装成 `Lease`（租约）：

```
ConcurrentHashMap<应用名, Map<实例ID, Lease<InstanceInfo>>>
                                    ↑
                     为什么要包一层租约？
```

因为 Eureka 的世界观是：**"注册"不代表"永远存在"，只代表"未来 90 秒内有效"**。
实例必须靠心跳不断续租，否则租约过期、实例被剔除。

这个设计源自 AWS 环境的现实：虚拟机随时可能被回收，根本来不及"优雅下线"。
与其指望实例好好告别，不如默认它会突然消失。

### 第四站：集群复制，"尽力而为"的异步广播

本地写入完成后，注册信息要传播给集群其他节点：

```java
// PeerAwareInstanceRegistryImpl.register()
super.register(info, leaseDuration, isReplication);              // ① 本地注册（同步）
replicateToPeers(Action.Register, ..., isReplication);            // ② 复制给peer（异步！）
```

注意：**①完成后客户端就收到 204 成功响应了**，②是异步的，甚至可能失败。

更狠的是复制的实现——它不是直接发 HTTP 请求，而是把任务丢进一个批处理队列：

- 500ms 内发往同一节点的复制任务会被**合并成一个批量请求**（最多 250 个）
- 同一实例的多次操作会被**去重**（只保留最新的）
- 任务积压超过 30 秒直接**丢弃**

丢弃？！注册信息丢了怎么办？

### 第五站：心跳，最终一致性的兜底

这就是 Eureka 设计中最精彩的部分：**复制丢了真的没关系**。

因为每个实例每 30 秒的心跳也会被复制给所有节点，而心跳复制带着数据版本号
（lastDirtyTimestamp），peer 节点收到后会做对账：

```java
// PeerEurekaNode.heartbeat() 的失败处理
if (statusCode == 404) {        // peer说:我没有这个实例
    register(info);              // → 把完整数据推过去（修复peer的缺失）
}
// statusCode == 409 时         // peer说:我的数据比你新
    → 用peer返回的数据覆盖本地     （修复自己的落后）
```

所以 Eureka 集群一致性的真相是：

> **复制是"尽力而为"的优化，心跳对账才是一致性的保证。**
> 任何数据丢失，都会在下一个心跳周期（30秒内）被发现并自动修复。

## 这就是 AP

把上面的旅程串起来，你会发现 Eureka 在每个环节都做了同样的选择：

| 环节 | CP 的做法 | Eureka（AP）的做法 |
|------|----------|------------------|
| 注册写入 | 多数派确认才返回成功 | 写本地立即返回，复制异步 |
| 复制失败 | 回滚或重试直到成功 | 记日志继续，心跳兜底 |
| 数据冲突 | 不允许发生 | 版本号比较，新者赢 |
| 网络分区 | 少数派拒绝服务 | 各分区独立服务，分区愈合后对账 |

**一句话总结**：Eureka 用"持续对账的循环"替代了"严格一致的协议"，用 30 秒级的数据延迟，
换来了任何单点故障、网络分区下的持续可用。
