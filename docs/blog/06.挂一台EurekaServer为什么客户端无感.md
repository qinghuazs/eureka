# 挂一台 Eureka Server 为什么客户端无感？装饰器链与故障转移

> 本文是《Eureka 源码深度解析》系列第 6 篇。这一篇研究一个平时"理所当然"的现象背后的代码。

## 理所当然的背后

配置三个 Eureka 地址：

```yaml
eureka.client.serviceUrl.defaultZone: http://e1:8761/eureka,http://e2:8761/eureka,http://e3:8761/eureka
```

运维重启了 e1，你的服务没有任何感觉。这件事是谁做到的？怎么做到的？

很多人答"客户端会重试"。对，但只对了三分之一。
完整的答案是一条四层装饰器链，每层解决一个独立的问题。

## 四层装饰器

客户端发出的每一个请求（注册/心跳/拉取），都要穿过这条链
（EurekaHttpClients.canonicalClientFactory 组装）：

```
SessionedEurekaHttpClient        会话层：解决"长期粘连一台Server"
  └ RetryableEurekaHttpClient    重试层：解决"单台故障"          ← 故障转移在这
      └ RedirectingEurekaHttpClient  重定向层：解决"302跳转"
          └ JerseyApplicationClient   干活层：真正发HTTP请求
```

### 重试层：故障转移的主角

核心逻辑（RetryableEurekaHttpClient.execute）：

```java
for (int retry = 0; retry < 3; retry++) {              // 最多3次
    EurekaHttpClient currentHttpClient = delegate.get(); // 上次成功的客户端（缓存）
    if (currentHttpClient == null) {
        // 没有缓存（首次或上次失败了）→ 从候选列表选下一个Server
        candidateHosts = getHostCandidates();
        currentEndpoint = candidateHosts.get(endpointIdx++);
        currentHttpClient = clientFactory.newClient(currentEndpoint);
    }
    try {
        response = requestExecutor.execute(currentHttpClient);
        if (serverStatusEvaluator.accept(response.getStatusCode(), ...)) {
            delegate.set(currentHttpClient);             // 成功 → 缓存它
            return response;
        }
    } catch (Exception e) { ... }
    
    // 失败 → 清缓存 + 拉黑这台Server
    delegate.compareAndSet(currentHttpClient, null);
    quarantineSet.add(currentEndpoint);                  // 进隔离区
}
throw new TransportException("Retry limit reached...");
```

三个要点：

1. **正常时零开销**：成功的客户端被缓存（delegate），后续请求直接复用，
   重试逻辑根本不执行。
2. **失败时换台重试**：当前 Server 进隔离区（quarantineSet），从候选列表换下一台。
   e1 挂了 → 第一次请求失败（耗时一个超时周期）→ 自动换 e2 → 成功。
   这就是"业务无感知"——其实有感知，就是那一次超时，但不会失败。
3. **隔离区自愈**：被隔离的 Server 不会永久拉黑。当隔离的数量超过总数的 66% 时，
   清空隔离区重新开始——"大多数都坏了"更可能是自己网络的问题。

### 会话层：防止"从一而终"

重试层有个副作用：客户端连上一台 Server 后就一直用它（缓存）。
后果是 Server 间负载不均——重启过的 Server 流量回不来，新扩容的 Server 没流量。

会话层的解法简单粗暴：**每 20 分钟（±50% 随机）强制丢弃缓存的客户端**，
逼着重试层重新选一台。

```java
if (delay >= currentSessionDurationMs) {
    currentSessionDurationMs = randomizeSessionDuration(sessionDurationMs);  // 随机化下次时长
    TransportUtils.shutdown(eurekaHttpClientRef.getAndSet(null));            // 丢弃,逼重选
}
```

为什么要随机化（±50%）？如果所有客户端都精确地每 20 分钟重连一次，
重连时刻会形成周期性的"重连风暴"。随机化把风暴打散成毛毛雨。

> **设计模式提炼**：缓存（重试层）解决性能，过期（会话层）解决均衡，二者天然矛盾，
> 用"带随机抖动的定期失效"调和。这个套路适用于一切"客户端侧负载均衡 + 连接复用"的场景。

## 两条独立的链

还有个细节：DiscoveryClient 里其实有**两条**这样的装饰器链：

| | registrationClient | queryClient |
|--|--------------------|-------------|
| 用途 | 注册/心跳/下线 | 拉取注册表 |
| Server列表来源 | 配置的 serviceUrl | 可配置为"从已拉取的注册表中找Eureka Server" |

分开的原因：写操作（注册/心跳）必须发给配置的"权威"地址；
读操作（拉取）可以更灵活——甚至可以从注册表里发现新加入的 Eureka Server（自发现）。

## 面试官视角

**Q：客户端配置了 3 个 serviceUrl，是负载均衡地用它们吗？**

加分回答：不是。客户端同一时刻只用**一台**（缓存的那台），其他两台是备胎。
只有当前这台失败、或 20 分钟会话到期时才会换。所以三台 Eureka Server 的客户端连接数
往往很不均匀——这是正常现象，不是故障。

## 一句话总结

"挂一台无感知"= 重试层的自动切换 + 隔离区的避让 + 会话层的定期再均衡。
这条装饰器链是装饰器模式在工程中最干净的应用之一：每层只解决一个问题，叠起来就是高可用。
