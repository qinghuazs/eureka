# Eureka 自我保护机制：保的是什么？为什么剔除不能同步给集群？

> 本文是《Eureka 源码深度解析》系列第 4 篇。这一篇讲实例的"死亡"——
> 主动下线、被动剔除、以及那个让无数测试环境头疼的红色警告。

## 那行红色大字

用过 Eureka 的人都见过控制台上这行字：

> **EMERGENCY! EUREKA MAY BE INCORRECTLY CLAIMING INSTANCES ARE UP WHEN THEY'RE NOT.
> RENEWALS ARE LESSER THAN THRESHOLD AND HENCE THE INSTANCES ARE NOT BEING EXPIRED
> JUST TO BE SAFE.**

翻译过来：自我保护触发了，过期的实例不剔除了。

大部分人对它的理解止步于"网络分区时的保护机制"。但有三个问题很少有人能答上来：

1. 阈值到底怎么算的？
2. 为什么测试环境几乎永远处于自我保护状态？
3. 为什么实例被"剔除"这件事不同步给集群其他节点？

## 实例死亡的两条路

先分清两个概念：

| | 主动下线（Cancel） | 被动剔除（Evict） |
|--|------------------|------------------|
| 触发 | 实例优雅停机时自己发 DELETE | 服务端定时任务发现租约过期 |
| 时效 | 立即 | 最长约 4 分钟（180s过期+60s周期） |
| 复制给集群 | ✅ 是 | ❌ **否** |
| 受自我保护限制 | ❌ 否 | ✅ 是 |

主动下线没什么可说的——实例自己发 DELETE，服务端删租约，复制给 peer，结束。

有意思的是被动剔除。它的执行者是一个每 60 秒跑一次的定时任务（EvictionTask），
而这个任务每次执行前都要先过三道关。

## 剔除的三道关

### 第一关：自我保护检查

```java
// 是否允许剔除？
return numberOfRenewsPerMinThreshold > 0
    && getNumOfRenewsInLastMin() > numberOfRenewsPerMinThreshold;
```

翻译：**最近一分钟收到的心跳数 > 阈值**，才允许剔除。

阈值怎么算的？

```java
this.numberOfRenewsPerMinThreshold =
    (int) (expectedNumberOfClientsSendingRenews     // 期望有多少客户端发心跳
        * (60.0 / 30)                                // 每个客户端每分钟该发2次
        * 0.85);                                     // 打85折
```

例：100 个实例 → 阈值 = 100 × 2 × 0.85 = 170。
如果最近一分钟全集群心跳数 ≤ 170，说明超过 15% 的实例同时"失联"——
Eureka 认为这不可能是 15% 的实例同时挂了，更可能是网络出了问题（或者 Eureka 自己出了问题），
于是停止剔除，保留所有数据。

**这就是 AP 的灵魂**：拿到一批可能过时的实例列表（调用方可以重试规避），
好过拿到一个空列表（整个微服务体系的调用关系瞬间蒸发）。

### 为什么测试环境永远在自我保护？

现在可以回答第二个问题了。测试环境通常只有两三个实例：

```
3 个实例 → 阈值 = 3 × 2 × 0.85 = 5.1 → 取整 5
```

随便一个实例重启或网络抖动，每分钟心跳数就从 6 掉到 4，低于阈值 5——自我保护触发。
而且实例数越少，统计波动越大，保护越容易误触发。

所以测试环境的标准做法就是关掉它：

```yaml
eureka.server.enable-self-preservation: false
```

### 第二关：剔除数量上限

就算允许剔除，单次也有上限：

```java
int registrySizeThreshold = (int) (registrySize * 0.85);
int evictionLimit = registrySize - registrySizeThreshold;    // 即注册表的 15%
int toEvict = Math.min(expiredLeases.size(), evictionLimit);
```

100 个实例最多一轮剔 15 个。就算真有 50 个实例同时过期，也要分 4 轮（4 分钟）慢慢剔——
每一轮之间，自我保护都有机会重新触发刹车。

### 第三关：随机剔除

```java
// Pick a random item (Knuth shuffle algorithm)
int next = i + random.nextInt(expiredLeases.size() - i);
Collections.swap(expiredLeases, i, next);
```

剔除不按顺序，按 Knuth 洗牌随机挑。为什么？
因为注册表的遍历顺序中，**同一个应用的实例是相邻的**。如果按顺序剔除 15 个，
很可能把某个应用的实例一锅端了。随机化把伤害平摊到所有应用——每个应用都掉一点，
但没有应用全军覆没。

> **设计模式提炼**：三道关组成的是一个"渐进式止损"系统——
> 全局熔断（自我保护）→ 限流（15%上限）→ 打散（随机化）。
> 任何不可逆的批量操作（删数据、下节点、清缓存）都值得照抄这个三层结构。

## 为什么剔除不复制？

最后回答第三个问题，这是整个机制里最精妙的细节。

看代码，剔除调用的是 `internalCancel()`，而主动下线调用的是 `cancel()`：

```java
// 主动下线：会被复制
public boolean cancel(...) {
    if (super.cancel(...)) {
        replicateToPeers(Action.Cancel, ...);    // 广播给集群
        ...

// 被动剔除：调 internalCancel，刻意绕过复制
internalCancel(appName, id, false);
```

为什么？假设剔除也复制：

1. 节点 A 因为没收到实例 X 的心跳，把 X 剔除了
2. A 把"X 下线了"复制给节点 B
3. B 收到后，把 X 当作"主动下线"处理 → B 的 expectedNumberOfClientsSendingRenews 减 1
4. B 的自我保护阈值跟着下降
5. 下次大面积网络故障时，B 的阈值已经被"温水煮青蛙"式地降低了——**该触发保护时不触发**

更深层的原因：**"我没收到 X 的心跳"不代表"X 死了"，只代表"X 到我的网络断了"**。
X 到 B 的网络可能是好的。所以剔除必须是每个节点根据自己的视角独立判断的事——
A 的判断不应该强加给 B。

这就是分布式系统设计里的一条铁律：**故障检测的结论不可传递。**

## 面试官视角

**Q：自我保护触发后，那些真死了的实例怎么办？调用方一直调用失败？**

加分回答：是的，自我保护期间死实例会残留，这是 AP 的代价。Eureka 的预期是调用方
必须有自己的容错（Ribbon 重试 + Hystrix 熔断把死实例隔离掉）。注册中心只保证
"列表大致可用"，不保证"列表里每一个都活着"——这个责任边界划分是理解 Eureka 的关键。

## 一句话总结

自我保护保的不是实例，是**注册表数据的完整性**：在无法区分"实例死了"和"网络断了"的时候，
选择相信实例还活着。配合 15% 限流和随机剔除，构成了 Eureka 面对故障时的"渐进式止损"体系。
