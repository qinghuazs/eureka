# Eureka 的心跳不只是保活：藏在续约里的分布式对账机制

> 本文是《Eureka 源码深度解析》系列第 2 篇。上一篇我们说到：注册的复制"丢了也没关系，
> 心跳会兜底"。这一篇就来兑现这个承诺——看看心跳到底是怎么兜底的。

## 从一个生产事故说起

某天凌晨，Eureka 集群的节点 B 因为 OOM 重启了。重启后它的注册表是空的，
按理说所有服务都"消失"了，依赖它的调用方应该大面积报错。

但实际上什么都没发生。15 分钟后值班同学看监控才发现 B 重启过——注册表已经恢复如初。

没有人工介入，没有数据恢复脚本。是谁把数据"还"给了节点 B？

答案是：**每一个客户端的心跳**。

## 心跳的明面工作：续租

先看心跳的本职工作。客户端每 30 秒发一次：

```
PUT /v2/apps/{appName}/{instanceId}?status=UP&lastDirtyTimestamp=1733123456789
```

服务端的处理轻得不能再轻（AbstractInstanceRegistry.renew()）：

```java
Lease<InstanceInfo> leaseToRenew = gMap.get(id);   // 查租约
if (leaseToRenew == null) {
    return false;                                   // 没有 → 404
}
renewsLastMin.increment();                          // 自我保护统计+1
leaseToRenew.renew();                               // 更新时间戳，完事
```

注意和注册的区别：**不加锁、不失效缓存、不进增量队列**。
因为续约是全系统最高频的操作（1 万实例 = 每秒 333 次心跳），必须把成本压到 O(1)。

### 顺带一提：那个著名的 Bug

```java
public void renew() {
    lastUpdateTimestamp = System.currentTimeMillis() + duration;   // 多加了 duration！
}
public boolean isExpired(long additionalLeaseMs) {
    return (System.currentTimeMillis() > (lastUpdateTimestamp + duration + ...));  // 又加一次
}
```

续约时间戳多加了一个 duration（90s），过期判断又加一次——实际过期时间是配置值的 **2 倍**（180 秒）。

Netflix 在注释里明确写了：知道是 bug，不修，因为改了影响面太大。
这是个很好的工程课：**有些 bug 活得久了，就成了规格的一部分。**

## 心跳的暗面工作：对账

重头戏来了。心跳请求里带的那个 `lastDirtyTimestamp` 参数，是客户端数据的"版本号"。
服务端续约成功后会做一次**版本比对**（InstanceResource.validateDirtyTimestamp）：

```
情况一：客户端版本 > 服务端版本
        说明服务端的数据旧了（比如服务端重启过、数据丢过）
        → 返回 404
        → 客户端收到后立即重新注册，把完整的新数据推上来

情况二：服务端版本 > 客户端版本（仅在节点间复制时处理）
        说明请求方的数据旧了
        → 返回 409 + 服务端的完整数据
        → 请求方用这份数据覆盖自己

情况三：版本一致
        → 返回 200，皆大欢喜
```

看到了吗？**404 和 409 不是错误，是数据修复指令。**

## 回到开头的事故

现在可以解释节点 B 的"自愈"了：

1. B 重启，注册表为空
2. 30 秒内，各客户端的心跳陆续到达 B
3. B 发现"我没有这个实例的租约" → 全部返回 404
4. 每个客户端收到 404，立即触发重新注册（带完整数据）
5. 几个心跳周期内，B 的注册表满血复活

同样的机制也工作在节点之间：A 给 B 复制心跳时如果 B 返回 404，
A 会把实例数据推给 B（PeerEurekaNode.heartbeat 的失败处理）：

```java
public void handleFailure(int statusCode, Object responseEntity) {
    if (statusCode == 404) {
        register(info);                              // 把实例注册到 peer（推数据）
    } else if (config.shouldSyncWhenTimestampDiffers()) {
        syncInstancesIfTimestampDiffers(...);        // 用 peer 的数据覆盖本地（拉数据）
    }
}
```

> **设计模式提炼**：与其设计一个"数据恢复流程"，不如让常规操作自带恢复能力。
> 心跳本来就要每 30 秒发一次——把对账逻辑挂在它身上，恢复机制就获得了和心跳一样的执行频率，
> 而且零额外成本。这叫"搭便车式容错"（piggyback）。

## 客户端这边的故事：指数退避

心跳是定时任务，但 Eureka 没用 `scheduleAtFixedRate`，而是自己写了一个 TimedSupervisorTask：

```
正常：     30s → 30s → 30s → ...
网络故障：  30s → 超时! → 60s → 超时! → 120s → 240s → 300s(封顶) → ... 
网络恢复：  → 心跳成功 → 30s → 30s（立即恢复正常频率）
```

为什么不用 fixedRate？因为网络故障时心跳必然超时，固定频率会让超时任务在线程池里堆积，
网络恢复的瞬间集中爆发。指数退避 + 自调度，让系统在故障时"安静下来"。

但这里有个隐患：退避上限 300 秒 > 租约实际过期时间 180 秒。
意味着长时间网络故障恢复后，实例可能已经被服务端剔除了，要等下一次心跳（最长 300 秒后）
收到 404 才会重新注册。**这是 Eureka 故障恢复慢的原因之一。**

## 面试官视角

**Q：Eureka 服务端重启后数据怎么恢复？**

普通回答："从其他节点同步。"（只对了一半——syncUp 确实存在，但它只在启动时执行一次）

加分回答："两层机制。启动时 syncUp 从 peer 节点拉一次全量；更重要的是运行期的心跳对账——
所有客户端的心跳会持续收到 404 并触发重新注册，几个心跳周期内数据自然恢复。
这也是为什么 Eureka 敢用纯内存存储、不做任何持久化。"

## 一句话总结

心跳在 Eureka 里是一鱼三吃：**保活**（更新租约）、**统计**（自我保护的数据来源，下下篇讲）、
**对账**（404/409 驱动的数据自愈）。理解了第三点，才算真正理解 Eureka 为什么敢叫自己 AP。
