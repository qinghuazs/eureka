# 新服务注册后为什么 90 秒才能被调用？扒一扒 Eureka 的三级缓存

> 本文是《Eureka 源码深度解析》系列第 3 篇。前两篇讲了数据怎么"写进"Eureka，
> 这一篇讲数据怎么"读出来"——以及为什么读出来的总是旧数据。

## 现象：发布完成，流量没来

每个用过 Eureka 的人都经历过：

- 新版本实例已经启动、注册成功，Eureka 控制台都能看到了
- 但流量就是不过来，要等一两分钟才慢慢有请求进来
- 老实例已经下线了，调用方却还在往它发请求，报一堆 Connection Refused

这不是 bug，是 Eureka 的设计。要理解它，得把"读路径"上的每一层缓存都数一遍。

## 服务端：注册表外面包着两层缓存

消费方调用 `GET /v2/apps` 拉取注册表时，请求**根本不会碰到注册表**，而是被两层缓存挡住：

```
请求 → readOnlyCacheMap（一级,只读缓存）
           ↓ 未命中
       readWriteCacheMap（二级,读写缓存,Guava）
           ↓ 未命中（被失效/180s过期）
       registry（真实注册表,双层Map） → 序列化+GZIP压缩 → 存入二级 → 回填一级
```

**为什么要缓存？** 因为缓存的不是对象，是**序列化+压缩之后的字节**。
1 万个客户端每 30 秒拉一次注册表，如果每次都遍历注册表+序列化 JSON+GZIP 压缩，
服务端 CPU 会被打爆。缓存让这个成本变成"每 30 秒一次"，和客户端数量无关。

**两层缓存怎么配合？**

| | 一级 readOnlyCacheMap | 二级 readWriteCacheMap |
|--|----------------------|------------------------|
| 数据结构 | 普通 ConcurrentHashMap | Guava LoadingCache |
| 更新方式 | **每 30 秒**从二级同步 | 注册/下线时**立即失效** + 180s 自动过期 |
| 读取性能 | 极致（无锁无回源） | 有回源可能 |

看到问题了吗？实例注册时只失效**二级**缓存，**一级缓存要等最多 30 秒的定时同步**才能看到新数据。
这是第一个 30 秒。

## 客户端：还有一层本地缓存

消费方的 DiscoveryClient 把整个注册表拉到本地内存（localRegionApps），业务代码
（Ribbon/Feign）做服务发现时**完全不发网络请求**，直接读这份本地缓存。

本地缓存每 30 秒刷新一次（CacheRefreshThread）。这是第二个 30 秒。

## Ribbon：第三层缓存

如果用 Spring Cloud + Ribbon，Ribbon 自己还维护了一份 ServerList 缓存，默认也是 30 秒刷新。
这是第三个 30 秒。

## 算总账

```
新实例注册成功
  → 服务端二级缓存失效（瞬间）
  → 服务端一级缓存同步（最多30s）
  → 消费方本地缓存刷新（最多30s）
  → Ribbon ServerList刷新（最多30s）
  
最坏情况：30 + 30 + 30 = 90 秒
```

这就是标题的答案。下线的感知同理（甚至更糟，意外宕机要先等 180 秒租约过期 + 60 秒剔除周期，
总共能到 5 分钟，下篇细讲）。

## 增量拉取：另一个精巧设计

客户端每 30 秒拉的不是全量注册表（那样太大了，万级实例的注册表序列化后好几 MB），
而是**增量**——最近 3 分钟的变更记录：

```
GET /v2/apps/delta
→ 返回: [实例A: ADDED, 实例B: DELETED, 实例C: MODIFIED]  (通常只有几KB)
```

增量数据来自服务端的 `recentlyChangedQueue`（注册/下线时写入，保留 3 分钟）。

但增量有个致命问题：**丢一条，本地数据就永远错了**。Eureka 的解法是 hashcode 校验：

```java
// 服务端在增量响应里附带全量数据的"指纹"
apps.setAppsHashCode(allApps.getReconcileHashCode());   // 形如 "UP_10_DOWN_2_"

// 客户端合并增量后，算自己的指纹比对
if (!reconcileHashCode.equals(delta.getAppsHashCode())) {
    reconcileAndLogDifference(...);    // 不一致 → 放弃增量，全量拉取覆盖
}
```

指纹算法很糙——就是按状态统计实例数量拼成字符串（"UP_10_DOWN_2_"）。
它检测不出"数量恰好相同但内容不同"的错误，但对实践中的增量丢失（数量必然变化）足够了。

> **设计模式提炼**：增量优化 + 廉价校验 + 全量兜底。
> 不要求增量机制本身完美，只要求"出错能被发现，发现后有兜底"。
> 这比设计一个"绝不出错的增量协议"便宜得多。

## 怎么让它快起来？

生产上常见的调优（按收益排序）：

```yaml
# 服务端：关掉一级只读缓存（少30秒,代价是读压力直达二级缓存）
eureka.server.use-read-only-response-cache: false

# 服务端：缩短剔除周期（针对下线感知）
eureka.server.eviction-interval-timer-in-ms: 5000

# 客户端：缩短拉取间隔（少最多25秒）
eureka.client.registry-fetch-interval-seconds: 5

# Ribbon：缩短ServerList刷新（少最多25秒）
ribbon.ServerListRefreshInterval: 5000

# 实例：缩短心跳和租约（针对意外宕机的感知）
eureka.instance.lease-renewal-interval-in-seconds: 10
eureka.instance.lease-expiration-duration-in-seconds: 30
```

调完之后感知延迟能从 90 秒压到 10 秒级。代价是 Eureka 服务端压力上升数倍——
这正是 Eureka 的设计哲学：**默认配置为"大集群、低开销"优化，不为"快速感知"优化。**

## 面试官视角

**Q：Eureka 的多级缓存为什么不用"写时同步更新"而用"定时同步"？**

加分回答：写时同步意味着每次注册/下线都要更新一级缓存，而一级缓存的存在意义就是
"读取零竞争"——如果写操作也来碰它，就需要加锁或 CAS，读性能优势就没了。
定时同步让读写彻底分离：写路径只动二级，读路径只碰一级，30 秒的延迟就是这个分离的代价。
本质是用**数据新鲜度**换**读写隔离**。

## 一句话总结

Eureka 的读路径是三层 30 秒缓存的叠加（服务端只读缓存 + 客户端本地缓存 + Ribbon），
90 秒的感知延迟不是缺陷而是定价——用延迟买吞吐。能调，但调之前想清楚你的集群规模配不配。
