# Eureka 集群复制的工程智慧：去重、攒批与"丢了也没关系"

> 本文是《Eureka 源码深度解析》系列第 9 篇。这一篇深入 util/batcher 包——
> 一套不到 1000 行、却把"高吞吐异步复制"做到极致的小框架。

## 先算一笔账

一个中等规模的微服务体系：

- 5000 个服务实例
- 3 个 Eureka Server 节点
- 每个实例每 30 秒一次心跳

每个 Server 收到心跳后要复制给另外 2 个节点，那么节点间的复制请求量是：

```
5000 实例 ÷ 3节点 × (1/30s) × 2个peer ≈ 每个节点每秒发出 111 个复制请求
```

每秒 111 个 HTTP 请求只为了同步心跳，这还没算注册、下线、状态变更。
HTTP 的建连、头部开销远大于这点 payload，纯属浪费。

Eureka 的解法：**不是减少要复制的数据，而是减少 HTTP 请求的次数**。

## 三层结构

复制任务从提交到发出，经过三层（AcceptorExecutor）：

```
任务提交 → [接收队列] → 调度线程 → [去重池+顺序队列] → 攒批 → [批量队列] → 工作线程 → 一个HTTP请求
              ↑                                                      |
              └──────────── 失败回流（重做队列）←──────────────────────┘
```

### 第一层机关：去重

每个任务有个 ID，比如 heartbeat#MY-APP/instance-1。
任务进入去重池（一个 Map）时，**相同 ID 的旧任务直接被新任务覆盖**：

```java
TaskHolder<ID, T> previousTask = pendingTasks.put(taskHolder.getId(), taskHolder);
if (previousTask == null) {
    processingOrder.add(taskHolder.getId());
} else {
    overriddenTasks++;       // 旧任务被覆盖（它白排队了）
}
```

业务含义：实例 A 在 500ms 的攒批窗口内心跳了两次（或先注册又马上心跳），
只有最后一个状态需要被复制——中间状态没有意义。

### 第二层机关：攒批

满足两个条件之一就打包发车（hasEnoughTasksForNextBatch）：

```java
if (pendingTasks.size() >= maxBufferSize) return true;     // 满250个,发车
// 或者:最老的任务已经等了500ms,不能再等了,发车
long delay = System.currentTimeMillis() - nextHolder.getSubmitTimestamp();
return delay >= maxBatchingDelay;
```

这是经典的 **size-or-time 攒批策略**（Kafka 的 batch.size + linger.ms 同款）。
打包后整批变成一个 HTTP 请求：POST /peerreplication/batch/。

每秒 111 个请求 → 攒批后每秒 2-4 个请求。**95% 以上的请求量消失了。**

### 第三层机关：分级失败处理

批量请求发给 peer 后，结果分四类（ReplicationTaskProcessor）：

| 结果 | 含义 | 处理 |
|------|------|------|
| Success | 成功 | 完事 |
| Congestion | peer 返回 503 / 读超时 | **整批回流重做**,且触发流量整形延迟 |
| TransientError | 网络连接失败 | 同上 |
| PermanentError | 4xx 等 | **丢弃**,记日志 |

流量整形（TrafficShaper）值得一提：拥塞后不是立即重试，而是让后续批次延迟发送
（拥塞延迟窗口），给 peer 喘息时间——这是 TCP 拥塞控制思想在应用层的复刻。

### 第四层机关（隐形的）：丢了也没关系

注意上面的"丢弃"和任务过期：

```java
if (holder.getExpiryTime() > now) {
    holders.add(holder);
} else {
    expiredTasks++;        // 过期任务,不发了,直接扔
}
```

任务积压超过过期时间（心跳任务是 30 秒）就直接丢弃。一个复制框架，居然理直气壮地丢数据？

是的，因为有系列第 2 篇讲的心跳对账兜底：丢掉的复制，30 秒内会被下一次心跳复制的
404/409 机制修复。**正因为有兜底，框架才敢用"丢弃"换取简单和高效**——
不需要持久化队列、不需要严格重试、不需要 exactly-once。

> **设计模式提炼**：可靠性不是每一层都要做到 100%，而是整个系统有一层兜底即可。
> 把可靠性集中到一个机制（心跳对账）上，其他所有环节都可以激进地为性能优化。
> 这叫"可靠性预算"——别处处付费，在一个地方付清。

## 数字总结

| 机制 | 默认参数 | 效果 |
|------|---------|------|
| 攒批 | 250个/批 或 500ms | 请求数降低 95%+ |
| 去重 | taskId 覆盖 | 消除冗余中间状态 |
| 任务过期 | 心跳30s/注册90s | 防积压 |
| 队列上限 | 10000 | 防内存爆炸 |
| 工作线程 | 20 | 并发发送 |
| 拥塞延迟上限 | 30s | 防雪崩 |

## 面试官视角

**Q：如果让你设计跨节点的数据复制，你会怎么设计？**

可以借 Eureka 这套讲：先问清楚一致性要求——如果业务能容忍秒级不一致且有对账兜底，
就用"异步攒批+去重+丢弃过期"的高吞吐方案；如果要求强一致，那就是另一个故事（Raft/Paxos）。
能根据一致性要求选择不同复杂度的方案，比张口就 Raft 更显工程判断力。

## 一句话总结

Eureka 复制框架的智慧浓缩成三句话：合并能合并的（攒批）、跳过没必要的（去重）、
放弃来不及的（过期丢弃）——因为可靠性已经被心跳对账统一兜底了。
