# 客户端冷启动兜底：当所有 Eureka Server 都连不上时

## 文档说明

本文档分析 Eureka 客户端的**冷启动容灾**——当客户端首次启动、却连不上任何一台 Eureka Server 时，如何通过 `BackupRegistry` SPI 兜底加载一份注册表，让应用不至于因为"注册中心全挂"而完全瘫痪。

- 兜底契约：`com.netflix.discovery.BackupRegistry`
- 默认实现（不兜底）：`com.netflix.discovery.NotImplementedRegistryImpl`
- 触发点：`DiscoveryClient#fetchRegistryFromBackup`
- 注入点：`EurekaClientConfig#getBackupRegistryImpl`

---

## 零、TL;DR

> **一句话摘要**：Eureka 把客户端容灾分两层——【已运行客户端】靠本地缓存 `localRegionApps` 扛住 Server 临时宕机；【冷启动客户端】首次全量拉取全部 Server 不可达时，走 `BackupRegistry` SPI 从二级存储（本地文件等）兜底加载一份注册表。默认实现 `NotImplementedRegistryImpl` 返回 `null`（即默认不兜底），需要时由 `eureka.backupregistry` 注入自定义实现。

- **复杂度域**：Simple（一个 SPI 接口 + 一个分支判断），但理念重要
- **业务入口**：`DiscoveryClient` 构造器中 `shouldFetchRegistry()` 为真时的初始化块（:449）
- **设计内核**：AP 思想在客户端侧的延伸——"宁可用一份可能过期的注册表，也不要因为注册中心全挂而完全瘫痪"

## 一、这套机制解决什么问题

服务发现客户端依赖注册表才能做远程调用。但"注册中心"本身也会出故障，要分两种情况看：

| 场景 | 客户端有没有注册表数据 | 怎么扛 |
|------|----------------------|--------|
| **已运行客户端** + Server 临时宕机 | 有（本地缓存 `localRegionApps`） | 周期刷新失败时静默重试，继续用旧缓存对外提供发现能力 |
| **冷启动客户端** + 全部 Server 不可达 | 没有（缓存是空的 `new Applications()`） | 走 `BackupRegistry` 从二级存储兜底加载一份 |

第一层是"被动韧性"：客户端启动成功后，`localRegionApps` 里已经有数据。后台刷新线程（`CacheRefreshThread`）周期性调 `fetchRegistry(false)`，即使 Server 全挂、拉取抛异常，`fetchRegistry` 也只是 `catch` 后 `return false`（DiscoveryClient.java:1075-1078），**不清空旧缓存**。所以已运行的客户端在 Server 宕机期间照常用过期数据做发现——这正是 Eureka 标榜的"AP，可用性优先"。

第二层才是本文重点：**冷启动时缓存是空的**。如果首次全量拉取也连不上任何 Server，客户端手里一份数据都没有。`BackupRegistry` 就是为这个"最坏开局"准备的最后一道防线。

## 二、涉及的核心类

| 类 / 方法 | 角色 | 关键点 |
|-----------|------|--------|
| `BackupRegistry`（接口） | 兜底注册表 SPI 契约 | 仅两个方法 `fetchRegistry()` / `fetchRegistry(String[] includeRemoteRegions)`；`@ImplementedBy(NotImplementedRegistryImpl.class)` |
| `NotImplementedRegistryImpl` | 默认实现 | 两个方法都 `return null`——**默认等于不兜底** |
| `DiscoveryClient#fetchRegistryFromBackup` | 兜底触发逻辑 | 拿到 backup 实例 → `fetchRegistry()` → 过滤洗牌 → 写入 `localRegionApps`（:1647） |
| `DiscoveryClient` 构造器初始化块 | 调用点 | 首次拉取失败后才调 backup（:456） |
| `EurekaClientConfig#getBackupRegistryImpl` | 注入开关 | 返回自定义实现的全限定类名；默认 `null` |
| `DefaultEurekaClientConfig#getBackupRegistryImpl` | 默认配置读取 | 读 `eureka.backupregistry` 属性，缺省 `null`（:203） |
| `localRegionApps` | 本地注册表缓存 | `AtomicReference<Applications>`，两层容灾的共同落点（:166） |

## 三、关键流程：fetchRegistry 成功/失败 → backup 分支

冷启动初始化发生在 `DiscoveryClient` 构造器的 `shouldFetchRegistry()` 分支里（:449-467）：

```mermaid
flowchart TD
    START([DiscoveryClient 构造<br/>shouldFetchRegistry=true]) --> PRIMARY[fetchRegistry(false)<br/>向主 Server 集群全量拉取]
    PRIMARY --> OK{拉取成功?}

    OK -- 成功 --> DONE([localRegionApps 已填充<br/>正常启动])

    OK -- "失败(全部Server不可达<br/>fetchRegistry返回false)" --> BACKUP[fetchRegistryFromBackup]
    BACKUP --> GETIMPL[取 BackupRegistry 实例<br/>= backupRegistryProvider.get]
    GETIMPL --> ISNULL{实例存在?}

    ISNULL -- "否(无定义)" --> WARN[日志: No backup registry instance defined<br/>返回 false]
    ISNULL -- 是 --> CALL["backupInstance.fetchRegistry()"]
    CALL --> APPSNULL{返回 apps 非空?}

    APPSNULL -- "空(NotImplementedRegistryImpl<br/>默认返回 null)" --> FALSE[返回 false]
    APPSNULL -- 非空 --> FILL[filterAndShuffle 过滤洗牌<br/>写入 localRegionApps<br/>日志: Fetched from the backup]
    FILL --> TRUE([返回 true<br/>用兜底数据启动])

    WARN --> ENFORCE
    FALSE --> ENFORCE
    ENFORCE{shouldEnforceFetchRegistryAtInit?<br/>默认 false}
    ENFORCE -- "true" --> THROW([抛 IllegalStateException<br/>启动失败])
    ENFORCE -- "false(默认)" --> EMPTY([带空缓存继续启动<br/>等后台刷新自愈])

    style BACKUP fill:#fff3cd
    style FILL fill:#e1f5e1
    style THROW fill:#ffe1e1
```

对照源码 `fetchRegistryFromBackup`（DiscoveryClient.java:1647-1680）：

```java
if (null != backupRegistryInstance) {
    Applications apps = null;
    if (isFetchingRemoteRegionRegistries()) {
        // 拉远程 region 时透传 region 列表
        apps = backupRegistryInstance.fetchRegistry(remoteRegionsStr.split(","));
    } else {
        apps = backupRegistryInstance.fetchRegistry();   // 默认实现返回 null
    }
    if (apps != null) {
        final Applications applications = this.filterAndShuffle(apps);
        applications.setAppsHashCode(applications.getReconcileHashCode());
        localRegionApps.set(applications);               // 兜底数据落入主缓存
        logger.info("Fetched registry successfully from the backup");
        return true;
    }
} else {
    logger.warn("No backup registry instance defined & unable to find any discovery servers.");
}
```

注意三点：① 兜底数据和正常拉取走**同一条洗牌/过滤管道**（`filterAndShuffle`），下游业务无差别对待；② 兜底数据直接写进 `localRegionApps`——和正常拉取的落点完全一致；③ 整个方法被 `try/catch(Throwable)` 包住，自定义实现抛异常也只会被吞成 `return false`，不会让客户端启动崩溃。

## 四、关键设计点 / 坑

1. **默认行为是"不兜底"**。`BackupRegistry` 上的 `@ImplementedBy(NotImplementedRegistryImpl.class)` 和 `getBackupRegistryImpl()` 默认返回 `null`，两条路都指向"返回 null"。绝大多数用户从没意识到这个扩展点存在——这是有意为之，因为兜底数据的来源（从哪读、是否可信、过期多久）是高度业务相关的，框架不替你决定。

2. **实例创建用反射 + 缓存**。构造器里的 `backupRegistryProvider`（DiscoveryClient.java:293-320）是个懒加载 `Provider`：第一次 `get()` 时读 `config.getBackupRegistryImpl()` 拿类名，`Class.forName(...).newInstance()` 反射创建（:302），失败则兜底回 `NotImplementedRegistryImpl`（:315）。这意味着**自定义实现必须有无参构造**。

3. **只在冷启动触发，不参与周期刷新**。`fetchRegistryFromBackup` 全局只有一个调用点（:456），就在构造器里。后台刷新线程的失败路径**不会**再走 backup——因为那时 `localRegionApps` 已有数据，旧缓存本身就是兜底。所以 `BackupRegistry` 的语义严格是"first time only"（见 `EurekaClientConfig#getBackupRegistryImpl` 的 Javadoc：*"as a fall back option for only the first time when the eureka client starts"*）。

4. **兜底失败后是否抛异常，由 `shouldEnforceFetchRegistryAtInit` 决定**（默认 `false`，DefaultEurekaClientConfig.java:429）。默认情况下，主拉取失败 + 兜底也失败，客户端**仍会带着空缓存继续启动**，赌后台刷新线程稍后能连上 Server 自愈。把它设为 `true` 则启动直接抛 `IllegalStateException`（DiscoveryClient.java:460-461）——适合"没有注册表就绝不能提供服务"的强一致诉求。

5. **数据新鲜度是你自己的责任**。框架把兜底数据当全量注册表处理（重算 hashCode、当作下次增量校验基准）。如果你的 backup 实现读的是一份很旧的快照，客户端会先用这份旧数据对外发现，直到第一次成功的周期刷新覆盖它。坑在于：旧快照里若有已下线的实例，启动初期可能打到死节点。

## 五、与 Spring Cloud 的连接

- Spring Cloud Netflix 沿用了这套机制但**几乎没有暴露开箱配置**——`spring.cloud.eureka.client.*` 里没有专门的 backup 入口，对应的原生配置键是 `eureka.client.backupregistry`（namespace `eureka.` + key `backupregistry`，见 `PropertyBasedClientConfigConstants.BACKUP_REGISTRY_CLASSNAME_KEY`）。
- Spring Cloud 默认通过容器注入 `BackupRegistry` Bean。若不显式提供，得到的就是 `NotImplementedRegistryImpl`，行为与原生一致——**默认不兜底**。
- 现象对应：很多人观察到"Eureka Server 全挂时，重启业务应用会报 `Cannot execute request on any known server`，但不重启的应用照常工作"。这正是两层容灾的直接体现——不重启的靠 `localRegionApps` 旧缓存，重启的因为没配 `BackupRegistry` 而拿不到任何数据。
- `eureka.client.enforce-fetch-registry-at-init`（对应 `shouldEnforceFetchRegistryAtInit`）默认 `false`，所以即便冷启动拉不到注册表，Spring Boot 应用通常也能起来，只是发现能力暂时为空。

## 六、常见问题 / 面试题

**Q1：Eureka Server 全部宕机，客户端会发生什么？要分情况吗？**
A：要分两种。**已运行客户端**手里有 `localRegionApps` 旧缓存，后台刷新虽然失败（`fetchRegistry` 返回 false）但不清空缓存，继续用过期数据做服务发现，业务基本无感。**冷启动客户端**缓存是空的，会尝试 `fetchRegistryFromBackup` 走 `BackupRegistry` 兜底；默认实现返回 null 即拿不到数据，此时若 `shouldEnforceFetchRegistryAtInit=false`（默认）就带空缓存启动等自愈，若为 true 则启动直接抛异常失败。

**Q2：`BackupRegistry` 默认能用吗？怎么启用自定义兜底？**
A：默认不能——默认绑定的 `NotImplementedRegistryImpl` 两个方法都返回 `null`。启用方式有两种：① 配置 `eureka.backupregistry=你的全限定类名`，框架会反射无参构造创建（DiscoveryClient.java:299-302）；② 在 DI 容器里直接注入一个 `BackupRegistry` 实现 Bean。实现里通常从本地文件 / 二级存储 / CMDB 读一份注册表快照返回。

**Q3：为什么 backup 只在启动时生效，不在后台刷新时兜底？**
A：因为后台刷新阶段 `localRegionApps` 已经有数据了，"上一次成功的缓存"本身就是更好的兜底——它一定比外部静态快照更新。所以 `fetchRegistryFromBackup` 全局只在构造器里调一次（:456）。这也体现 AP 取舍：能用相对新的内存缓存，就不退化到可能很旧的外部快照。
