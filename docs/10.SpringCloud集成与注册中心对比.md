# Spring Cloud 集成原理与注册中心横向对比

## 文档说明

本文档回答两个"向外看"的问题：

1. **Spring Cloud Netflix 是怎么包装本仓库代码的**——平时用的 `@EnableEurekaServer` 和这里的源码是什么关系
2. **Eureka 与 Nacos / Consul / Zookeeper 的本质区别**——基于本仓库源码细节的对比，而非泛泛而谈

---

## 第一部分：Spring Cloud 集成原理

### 1.1 依赖关系：Spring Cloud 只是"壳"，内核就是本仓库

```
spring-cloud-starter-netflix-eureka-server
└── spring-cloud-netflix-eureka-server
    └── com.netflix.eureka:eureka-core      ← 就是本仓库的 eureka-core
    └── com.netflix.eureka:eureka-client    ← 就是本仓库的 eureka-client

spring-cloud-starter-netflix-eureka-client
└── spring-cloud-netflix-eureka-client
    └── com.netflix.eureka:eureka-client    ← 同上
```

**结论**：本仓库学到的所有机制（注册表/三级缓存/自我保护/复制），在 Spring Cloud 中原封不动地存在，Spring Cloud 做的只是"装配方式"的替换。

### 1.2 服务端：@EnableEurekaServer 替换了什么

| 本仓库（原生） | Spring Cloud 替换为 | 替换的本质 |
|---------------|--------------------|-----------|
| war 包 + Servlet 容器 | Spring Boot 内嵌 Tomcat | 部署形态 |
| web.xml 注册 EurekaBootStrap | `EurekaServerAutoConfiguration` + `EurekaServerInitializerConfiguration` | **启动入口**（见下） |
| EurekaBootStrap.initEurekaServerContext() 手动 new 各组件 | Spring Bean 定义（@Bean PeerAwareInstanceRegistry 等） | 组件装配方式 |
| Jersey 1.x Servlet（web.xml 配置） | Spring Cloud 用 Jersey Filter 桥接进 Spring MVC | REST 路由接入 |
| eureka-resources（JSP Dashboard） | Freemarker 模板重写的 Dashboard | UI |
| 配置：eureka.* 属性文件（Archaius） | application.yml（eureka.server.* / eureka.client.* / eureka.instance.*） | 配置体系（Spring 的 EurekaServerConfigBean 实现了本仓库的 EurekaServerConfig 接口） |

**关键映射**——Spring Cloud 的配置类实现的就是本仓库的接口：

| Spring Cloud 配置类 | 实现的本仓库接口 | application.yml 前缀 |
|--------------------|----------------|---------------------|
| `EurekaServerConfigBean` | `com.netflix.eureka.EurekaServerConfig` | eureka.server.* |
| `EurekaClientConfigBean` | `com.netflix.discovery.EurekaClientConfig` | eureka.client.* |
| `EurekaInstanceConfigBean` | `com.netflix.appinfo.EurekaInstanceConfig` | eureka.instance.* |

所以 yml 里写的 `eureka.server.eviction-interval-timer-in-ms: 60000`，最终就是本仓库 `DefaultEurekaServerConfig.getEvictionIntervalTimerInMs()` 的替代实现返回的值——**所有配置语义在本仓库文档（01-09）中都已分析过**。

### 1.3 客户端：@EnableDiscoveryClient 替换了什么

| 本仓库（原生） | Spring Cloud |
|---------------|--------------|
| 手动 new DiscoveryClient(applicationInfoManager, config) | `EurekaClientAutoConfiguration` 自动创建 CloudEurekaClient（继承本仓库 DiscoveryClient） |
| 调用 eurekaClient.getInstancesByVipAddress() | Spring 的 `DiscoveryClient` 接口（getInstances()）→ 适配器转调本仓库 API |
| 与 Ribbon 手动集成 | `RibbonEurekaAutoConfiguration` 自动把本仓库的注册表数据灌给 Ribbon ServerList |
| 实例信息手动构建 | 从 Spring 环境自动推断（端口/IP/上下文路径） |

**CloudEurekaClient 对 DiscoveryClient 的扩展**只有一处实质增强：缓存刷新后发布 Spring 事件（`HeartbeatEvent`），供 Ribbon/LoadBalancer 感知。

### 1.4 学完本仓库后，Spring Cloud 的常见问题秒懂

| Spring Cloud 现象 | 本仓库源码解释 |
|------------------|---------------|
| 服务下线后调用方还能调到，持续约 1-2 分钟 | 文档 03/04：多级缓存延迟 + 客户端缓存 + Ribbon 缓存叠加 |
| eureka.client.registry-fetch-interval-seconds 调小不完全生效 | 文档 03：服务端 readOnly 缓存 30s 同步是另一层延迟 |
| 测试环境实例总是不被剔除 | 文档 04：实例少 → 自我保护常年触发（关闭 enable-self-preservation） |
| 注册的 IP 不对 | EurekaInstanceConfigBean 推断逻辑选了错误网卡（prefer-ip-address + ip-address 配置） |
| Server 互相注册形成集群的配置 | 文档 05：Server 即 Client，eureka.client.serviceUrl 指向彼此 |

## 第二部分：注册中心横向对比

### 2.1 本质差异总表

| 维度 | **Eureka**（本仓库） | **Nacos** | **Consul** | **Zookeeper** |
|------|---------------------|-----------|------------|---------------|
| **CAP 取舍** | AP（可用性优先） | AP + CP 可切换（临时/持久实例） | CP（Raft） | CP（ZAB） |
| **一致性协议** | 无协议：异步复制+心跳对账（最终一致） | Distro（AP）/ Raft（CP） | Raft | ZAB |
| **健康检测** | 客户端心跳上报（30s）| 客户端心跳(临时实例) / 服务端探测(持久实例) | 服务端主动探测（TCP/HTTP/脚本） | 会话+临时节点 |
| **数据模型** | 双层Map（应用→实例→租约） | 服务→集群→实例 | 服务→实例+KV存储 | ZNode 树 |
| **服务发现方式** | 客户端全量缓存+增量拉取 | 推送(UDP/gRPC)+拉取 | DNS / HTTP API + blocking query | Watch 机制 |
| **网络分区行为** | 自我保护:保留数据继续服务 | AP模式同Eureka / CP模式少数派不可写 | 少数派分区不可用 | 少数派分区不可用 |
| **多数据中心** | Region/Zone（AWS概念） | 命名空间+集群 | 原生多DC | 不支持 |
| **维护状态** | ❌ 2.x 停止开发,1.x 维护模式 | ✅ 活跃（阿里） | ✅ 活跃（HashiCorp） | ✅ 活跃（但不推荐做注册中心） |

### 2.2 基于源码细节的深度对比

**① 一致性 vs 可用性的真实代价（Eureka vs CP系统）**

本仓库源码中可见的 Eureka"不一致窗口"：
- 注册后其他客户端最长 90s 才可见（文档 03 多级缓存）
- 节点间复制是异步的，复制失败靠心跳分钟级修复（文档 02/05）
- 剔除各节点独立判断，集群视图短暂分歧（文档 04）

CP 系统（Consul/ZK）：写入需要多数派确认才返回——注册立即全局可见，但代价是：
- 网络分区时少数派**完全不可用**（连查询都拒绝）
- Eureka 的哲学：调用方拿到一个稍旧的实例列表，比拿不到列表好（拿到死实例可以重试，拿不到列表只能失败）

**② 健康检测模型的差异**

```
Eureka:  实例 --30s心跳--> Server（被动记账,见文档02）
         检测延迟 = 90s租约(实际180s) + 60s剔除周期 ≈ 4分钟

Consul:  Server --主动探测--> 实例的健康检查接口
         检测延迟 = 探测间隔(可配置到秒级)

Nacos:   临时实例=心跳(5s间隔,15s不健康,30s剔除) → 比Eureka快一个数量级
```

Eureka 检测慢的根源在本仓库源码里清晰可见：心跳间隔 30s 是写死在 LeaseInfo 默认值里的文化惯性 + renew() 的 2倍duration bug + 自我保护的保守主义。

**③ 推送 vs 拉取**

本仓库的客户端只有"拉"（30s 周期，文档 03）。Nacos/Consul 支持服务端推送变更（UDP push / blocking query），变更感知从"分钟级"进入"秒级"。这是 Eureka 架构上最落后的一点。

**④ 功能面差异**

| 功能 | Eureka | Nacos | Consul |
|------|--------|-------|--------|
| 服务注册发现 | ✅ | ✅ | ✅ |
| 配置中心 | ❌ | ✅ | ✅(KV) |
| 权重/保护阈值 | ❌ | ✅ | ❌ |
| 标签路由元数据 | metadata(Map) | ✅ 丰富 | ✅ tags |
| 控制台 | 简陋(JSP) | 完善 | 完善 |

### 2.3 选型建议（2026 视角）

| 场景 | 推荐 | 理由 |
|------|------|------|
| 新项目（国内） | **Nacos** | 注册+配置一体,AP/CP可选,中文生态,活跃维护 |
| 新项目（海外/多云） | **Consul** | 多DC原生支持,服务网格集成(Connect) |
| 存量 Spring Cloud Netflix 体系 | 维持 Eureka 或迁移 Nacos | Eureka 1.x 仍稳定可用,但无新特性 |
| K8s 环境 | K8s Service + CoreDNS（不需要独立注册中心） | 平台原生能力 |
| 学习分布式系统设计 | **读 Eureka 源码**（本仓库） | AP 设计的教科书,代码量适中,机制完整 |

### 2.4 为什么仍然值得学 Eureka 源码

1. **AP 注册中心的完整范本**：自我保护、多级缓存、心跳对账、最终一致——这些设计思想在 Nacos 的 AP 模式（Distro 协议）中大量复用
2. **面试深度区分度**：能讲清楚"自我保护阈值怎么算的""为什么剔除不复制""三级缓存为什么这么设计"的人，和只会背"Eureka 是 AP"的人，差距一目了然
3. **代码量适中**：核心逻辑约 2 万行，一周可以读完；Nacos 30 万行+，作为第一个源码学习对象门槛过高
